### 3.4 真机验证

> **本机 adb 必须走容器（2026-10-31 第 19 轮实测，重要）**
>
> 本机命令执行环境的 `/dev` 是被替换过的最小集，**没有 `/dev/bus/usb`**；手动
> `mount -t usbfs none /dev/bus/usb` 也被拒（无 CAP_SYS_ADMIN），`dangerouslyDisableSandbox` 同样无效。
> 所以在本机直接跑 `adb devices` **恒为空**，而 `lsusb` 却能列出设备——很容易误判成"线没插好"。
>
> 真正的通路：Docker daemon 跑在宿主上，能看到宿主真实 `/dev/bus/usb`。用
> `--privileged -v /dev/bus/usb:/dev/bus/usb` 挂进 `hostroot:1` 容器，容器内 adb 才能枚举。
> **只 `-v` 挂目录不够**：device cgroup 仍会拦，节点存在但 `head` 打不开，adb 照样空白。
>
> 已固化为 `/home/s/build/adb-usb.sh`，参数原样透传：
>
> ```bash
> /home/s/build/adb-usb.sh devices -l
> /home/s/build/adb-usb.sh install -r <apk>
> /home/s/build/adb-usb.sh shell "wm size"
> /home/s/build/adb-usb.sh exec-out screencap -p > shot.png
> ```
>
> 注意容器内还要 `mkdir -p /tmp`（否则 adb daemon 起不来），脚本已处理。

#### 3.4.3 出厂播种别用一次性标记位（第 20 轮踩的坑）

第一版 `FactoryDefaults` 在 SharedPreferences 里写 `factory_csp_seeded` / `factory_danmaku_seeded`，
「播种成功就置真，之后永不重复」。结果真机验证时**完全不播种**，原因是：

1. 装完包先启动了一次（那时 `registry.json` 还在）→ 走「已有配置 → 置标记 → return」分支，标记已经为真；
2. 之后把 `registry.json` 删掉再启动 → 一进门就 `if (Prefers.getBoolean(KEY_CSP_SEEDED)) return;`，直接放弃。

也就是说：**标记位把「这次不需要播种」错误地固化成了「永远不需要播种」**。
凡是「判断依据是外部配置、而状态记在别处」的幂等逻辑，都不要用一次性标记位，
直接判断那个外部配置本身存不存在即可 —— 天然幂等，且配置被系统/升级/卸载清掉后能自动补回。

顺带一个排查经验：这个 App 的 `run-as` 不可用（release 签名、非 debuggable），
`/data/data` 下的 prefs 读不到，所以**不要指望靠日志或 prefs 判断播种有没有执行**；
`SpiderDebug.log` 还受 `DebugLogStore.enabled` 开关控制，默认关，logcat 里根本不会出现。
判据只认文件系统里那个产物（`/sdcard/TV/CustomCsp/registry.json`）是否真的出现。

### 30.1 任务一：横屏形态判定回归修正

- **需求**：第 29 轮把「横屏」当成一类形态，平板横屏也被塞进手机横屏样式（底栏 3 胶囊搬进顶栏、隐藏状态栏、顶栏贴顶）。要求平板横屏恢复「保留底栏 + 正常状态栏 + 顶栏按安全区下移」，手机横屏保持 8 胶囊 + 隐藏状态栏，竖屏布局不动；8 胶囊那套尺寸只在手机横屏生效；状态栏隐藏改为运行时按形态设置。
- **方案**：把「横屏」拆成「手机横屏」——判定改用设备形态，**只有 `横屏 && 非平板`（`ResUtil.isPad()`，即设备模式 / `smallestScreenWidthDp` / sw600dp）才走 8 胶囊 + 隐藏状态栏**；平板横屏回退到竖屏式 5 胶囊 + 底栏 + 正常行高，状态栏不隐藏，顶栏按 `current.getSafeTop()` 下移。
- **改动文件 / 函数**：
  - `mobile/ui/activity/HomeActivity.java#applyDeviceAdaptation`：新增 `phoneLandscape = landscape && !ResUtil.isPad()`，只用它决定 `mChrome.setAdaptiveLayout(...)` 与内联导航可见性（`hideNavigation = phoneLandscape && mManager.isVisible(0)`）。

  - `mobile/ui/activity/WebHomeChromeController.java#setAdaptiveLayout`：形态变化时 `ViewCompat.requestApplyInsets(binding.getRoot())`，状态栏恢复后容器重新按安全区留白。
- **判定差异（一句话）**：**横屏 && 非平板才走 8 胶囊 + 隐藏状态栏；平板横屏保留底栏与状态栏、顶栏按安全区下移；竖屏逻辑未动。**

### 30.2 任务二：缓存按体积自动清理（对齐 TVBox 口径）

| 项 | WebHTV 实现 |
|---|---|
| 档位 | 100 / 200 / 300 / 500 / 1024 MB（`Setting.AUTO_CLEAR_CACHE_LIMITS`；1024 显示为「1 GB」） |
| 默认值 | 自动清理开关**默认关闭**；上限默认 **300 MB**（`DEFAULT_AUTO_CLEAR_CACHE_MB`，非法值回落 300） |
| 触发时机 | **冷启动 / 进程启动时**：`App.startBackgroundServices()` 在 `Server.get().start()` 之后 `Task.execute(FileUtil::autoClearCacheIfNeeded)`，后台线程静默执行，不阻塞启动、不弹提示 |
| 清理条件 | 开关关闭直接返回；缓存目录总大小 < 上限返回；≥ 上限才清理 |
| 清理范围 | 整个 `Path.cache()`（`getCacheDir()`）逐项 `Path.clear`，**保留 `update.apk`**（已下载待安装的更新包） |
| 持久化 | 沿用 WebHTV 现有 `Prefers`：`auto_clear_cache` / `auto_clear_cache_limit_mb` |

- **改动文件 / 函数**：
  - `setting/Setting.java`：新增 `AUTO_CLEAR_CACHE_LIMITS`、`DEFAULT_AUTO_CLEAR_CACHE_MB=300`、`isAutoClearCache` / `putAutoClearCache` / `getAutoClearCacheLimitMb` / `putAutoClearCacheLimitMb`（非法值回落默认）/ `isAutoClearCacheLimit` / `formatAutoClearCacheLimit`。
  - `utils/FileUtil.java`：新增 `autoClearCacheIfNeeded()`（按上表口径，含中文注释）。
  - `App.java#startBackgroundServices`：启动时后台调用一次。
  - `SettingFragment.onCache`：从「清缓存确认框」改为 `CacheCleanDialog.show(requireActivity(), this::setCacheText)`；新增 `ui/dialog/CacheCleanDialog.java` 与 `res/layout/dialog_cache_clean.xml`（标题 + 当前占用、自动清理开关行、上限档位行、说明行、48dp「立即清理」按钮；关闭或操作后刷新设置页缓存文案）。
  - 三语文案：`values/strings.xml`、`values-zh-rCN/strings.xml`、`values-zh-rTW/strings.xml` 在 `setting_cache` 后新增 `cache_manager_title` / `cache_current` / `cache_current_loading` / `cache_auto_clear` / `cache_limit` / `cache_limit_tip` / `cache_enabled` / `cache_disabled` / `cache_auto_on` / `cache_auto_off` / `cache_clear_now` / `cache_cleared`（zh-rTW 用「暫存」）。
- **「立即清理」是否重启 —— 待用户确认**：TVBox 手动清缓存后会重启 App；WebHTV 目前**清完不重启**，只 toast「已清理」并刷新占用数字。若要 1:1，需在 `CacheCleanDialog` 清理回调后加重启（会中断播放器/网页状态），确认后再改。
