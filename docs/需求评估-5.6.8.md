## 1. 首次启动不询问权限，用到才问

### 现状（已核实）

- 手机端 `mobile/.../HomeActivity.java:102` 在 `initView()` 里**无条件**调 `PermissionUtil.requestFile(...)`；
  电视端 `leanback/.../HomeActivity.java:160` 首帧后 1.8s 同样调用。
- `PermissionUtil.java:21-33`：没权限且 `Setting.hasFileManager()` 为真 → 经 PermissionX 起
  `ACTION_MANAGE_APP_ALL_FILES_ACCESS_PERMISSION`，**直接跳到系统「所有文件访问」页**。
- **没有任何「已经问过」的记忆**（无 prefs 标记）→ 只要没授权，**每次冷启动都会跳**。
- 真正判定在 `Setting.java:907-910`：Android 11+ 一律看 `Environment.isExternalStorageManager()`。

### 「安装即自动授权」可行吗

**不可行。** `MANAGE_EXTERNAL_STORAGE`（所有文件访问）从 Android 11 起**只能由用户在系统设置里手动打开**，
没有安装期自动授予的通道，也不允许应用自己申请弹窗（只能跳设置页）。三条可选路线：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 懒请求（推荐）** | 删掉两个 `HomeActivity` 的启动请求；只在真正要写 `/sdcard` 的功能入口请求（站点注入、备份恢复、文件管理、下载目录、管理页——这些位置**已经在请求了**，见 §附录） | 新装用户首页不再被弹走；首次进站点注入时才问 |
| **B. 降级判定** | 本项目 `targetSdk=28`，理论上可用 legacy `READ/WRITE_EXTERNAL_STORAGE` 替代「所有文件访问」。把 `hasFileAccess()` 改成「MANAGE **或** legacy 读写任一可用」，新装时只需点一次系统「允许」弹窗 | **需真机实测** Android 13 上 legacy 是否仍能读写 `/sdcard/TV`、`/sdcard/Download`；不保证一直有效（未来系统收紧） |
| **C. A+B 组合** | 平时用 B 的轻量权限，重功能（站点注入写文件）再按需升级到 MANAGE | 两条路径都要维护，复杂度最高 |

**建议**：先做 A（当天可验），B 作为可选增强，真机验过再定。

> 注意：A 做完后，出厂播种（`FactoryDefaults`）在**没权限的情况下仍然会失败**，
> 需要配合「授权后补种」一起做（这是上一轮真机测试暴露的问题）。

## 2. 个人中心：自动同步 + UI 一屏

### 2.1 自动同步

**现状**：已经有相当完整的同步底座，但**没有「数据改了 → 自动同步」的聚合入口**。

- 现成的同步能力（都不用重写）：
  - `AccountSync.sync(mode, cb)` / `upload()` / `restore()` —— `AccountSync.java:102 / 151 / 215`
  - 追更云备份防抖范式：`KeepCloudBackup.schedule(30s)`，静态 Runnable 去重（`KeepCloudBackup.java:31,40`）
  - 播放进度推送节流：`PlaybackWebhookSender`（同源只留一个延迟任务，`PlaybackWebhookSender.java:37-51`）
  - 启动钩子：`App.startBackgroundServices()`（`App.java:133-143`），已挂了 `AccountSync.bindIfNeeded()`、`KeepCloudBackup.restoreIfEmpty()`、`PlaybackRemoteSyncer.start()`
- **缺口（要新增打点的地方）**：
  1. `History.save()`（`History.java:410`）—— 完全没有任何事件/同步
  2. 所有 `Setting.putXxx()`（约 50 处，直写 `Prefers`）—— 无回调。可用 `Prefers.getPrefers().registerOnSharedPreferenceChangeListener` 统一兜（全工程目前 ZERO 处注册）
  3. `Keep.deleteAll()/delete(cid)/delete(key)`（`Keep.java:58-68`）—— 批量删除**漏挂**同步，只有实例 `save()/delete()` 挂了
- **「退出时自动备份」的难点**：工程**没有可靠的退出时机**。`HomeActivity.onDestroy()`（`:465`）只在正常销毁时回调，进程被杀不回调；工程也没引 WorkManager。
  → 可行做法：`App.onActivityStopped` + `ProcessLifecycleOwner` 判「退到后台超过 N 秒」即视为退出，做一次收敛式上传。
- **两套 prefs 白名单不一致**（`Backup.APP_PREFS` 93 项 vs `CloudConfigSync.EXCLUDED_PREFIX` 黑名单）：
  自动同步会把口径差异放大（有把 `account_token` 之类环回键同步出去的风险），**建议先合并成一份「可同步键」清单**再开自动同步。

**方案（建议拆成两步）**

- 第一步（中）：新增 `SyncScheduler`——dirty 标记 + `App.post(runnable, 8000)` 防抖 → `AccountSync.sync(MODE_MERGE)`；
  打点补到 History.save / Keep 批量删除 / SharedPreferences 监听；启动时若已登录则 `upload()` 一次；退后台 30s 收敛一次。
- 第二步（小）：把两套 prefs 白名单统一，避免同步脏键。

### 2.2 UI 一屏不滚动

**现状的硬障碍**（这条是整个需求里最费工的一项）：

- 个人中心**不是页面，是一个 Java 动态拼装的 Dialog**（`AccountDialog.java:187-220` + `dialog_account.xml`，只有一套布局、无 qualifier）。
- 内容区是 `CustomNestedScrollView`（`maxHeight=520dp`），一级菜单 = Hero 卡 + 2 个入口卡 + 安全卡，横屏手机高度装不下 → 必然滚动。
- **横竖屏切换尺寸不重算**：`HomeActivity` 自己消费了 `orientation|screenSize`（`mobile/AndroidManifest.xml:23`），
  Dialog 不重建，而尺寸只在 `onStart()` 算一次（`AccountDialog.java:105-132`）→ 转屏后宽高/限高是过期值。

**方案**

| 方案 | 内容 | 改动量 |
|---|---|---|
| **B1. 横屏双列（推荐）** | Hero 卡通栏，下面 2 个入口卡 + 安全卡改成 2 列网格；竖屏保持单列但压缩卡片高度（去掉统计四宫格的第二行） | 中：重写 `AccountDialog` 的 render 布局 + 加 `onConfigurationChanged`/`addOnLayoutChangeListener` 重算 |
| B2. 独立页面 | 个人中心从 Dialog 升级成 Activity（像设置页一样），可用 qualifier 出 4 套布局 | 中大：入口、返回栈、状态同步都要改 |
| B3. 只做「不滚动」 | 保持 Dialog，把 4 个区块压成一张紧凑卡（统计变一行文字），横屏强制限高内 | 小：但信息密度高、观感差 |

> 顺带：设置页 `fragment_setting.xml` 是 13 行 × 16dp 手写 LinearLayout，竖屏也必然滚动。
> 如果你说的「一级菜单一页显示全」也包括设置页，那要把它改成 RecyclerView + GridLayoutManager（横屏/平板 2~3 列）。

## 3. 设备模式 / 分辨率自适应

### 现状：**已经实现了**，不用重做

- 设置里已有「设备模式」：**自动 / 手机 / 平板**（`AppearanceDialog.java:44,54,105-110`，
  文案 `setting_device_mode` + 数组 `select_device_mode`）。

- `Setting.wrapDeviceMode()`（`:514-522`）还会**改写 Configuration 的 smallestScreenWidthDp**，

- 全项目布局判定都走 `ResUtil.isPad()` → `Setting.isPadDevice()`。

### 建议只做「验证 + 补漏」

1. 真机回归三种设备模式 × 横竖屏共 6 种组合，记录哪些页面没跟上（首页、设置、播放、详情、下载）。

   可在 `HomeActivity.applyDeviceAdaptation()`（`:241-248`）里加「实际窗口宽度」判据。

**结论：这一条基本是现成的，我建议合并到验证清单，不单独开需求。**

## 4. 起播即滚动弹幕

### 现状（已核实）

- 触发点：`VideoActivity.java:1985-1987` —— **等播放接口返回后**才 `DanmakuApi.search(...)`。
- 自动模式按来源**串行**试（`DanmakuApi.java:115-123`），每个源先 GET 再 POST，单源超时 12s/45s，
  **自动模式没有总超时**（`FIRST_RESULT_TIMEOUT_MS=6000` 只在「合并所有源/手动搜索」生效）。
- 出厂默认 8 个源全启用，第一条是 IP 直连源 → 第一条慢就整体慢。
- **没有弹幕缓存**：换集、切内核、切解码、重进页面都会重新搜索 + 重新下载整包。
- 首帧空窗的真正原因在库层：装载完成后 `applySortedItems()` → `syncToPlayer(true)` → `start(positionMs)`
  → `resetActivationCursor(positionMs)`（`media3-ui-danmaku` 的 `DanmakuController.java:732-739` / `DanmakuView.java:423-424`）。
  **游标被重置到当前进度，载入前时间轴上已有的弹幕一律不补显**，只能等「载入之后的下一条」。

### 方案分两档

| 档位 | 内容 | 改动量 |
|---|---|---|
| **中（建议先做）** | ① 搜索前移：详情页/选集页就按「剧名」预搜索并缓存结果（按 `vodName` 做 LRU，10~20 条）；② 自动探源改**并行先到先用**，加 3~5s 总超时；③ 拿到结果立刻 `setDataSource`（不等 `onPlaybackStateChanged`） | 中：`DanmakuApi` + `VideoActivity` + 新增缓存类 |
| 大（可选） | 改 `third_party/maven/.../media3-ui-danmaku` 的行为：装载完成后**回填当前时间点之前 N 秒的弹幕**（把 `resetActivationCursor` 改成「游标回退 3~5s」） | 大：需重编 AAR + 自建 fork 维护 |

**建议**：先做「中」，观感上从「等 5~10 秒」变成「1~2 秒内开始有弹幕」；「第一帧就有历史弹幕滚」再单独立项。

## 5. 检查更新逻辑（这里有个真 bug，必须先修）

### 现状：**「已是最新」也会提示有新版本，并且会重新下 150MB**

- `Update.hasUpdate()`（`bean/Update.java:42-45`）：
  ```java
  return code != BuildConfig.VERSION_CODE || !AppVersion.isCurrent(name);
  ```
  而 `AppVersion.isCurrent(name)`（`utils/AppVersion.java:16-18`）是拿 `name` 和「构建 tag / 版本号-构建时间」做**字符串全等**。
- 线上清单里 `name` 是**资产文件名** `mobile-arm64_v8a.apk`，永远不可能等于 `5.6.7-<构建时间>`
  → **`hasUpdate()` 恒为 true**。
- 于是：本地就是 5.6.7，点「检查更新」仍然显示「发现新版本 5.6.7，点击更新」，点下去**重新下载 150MB**。
- 另外两个确定的缺陷：
  - **没有下载互斥**：`check()`（`Updater.java:115-124`）与 `startDirectDownload()`（`:144-158`）都不看 `downloading` 标志；
    关掉「关于」再重开 → 再点提示条 → 会并发写同一个 `cache/update.apk`（旧 `transfer` 不 cancel，`:488`）。
  - **没有「待安装」记忆**：下载完直接 `FileUtil.openFile()` 拉系统安装器（`:604`），用户取消安装后什么都不记；下次启动不提示，且再点检查又会重下。

### 方案（都是小改）

1. **修版本比较**：改成「`code > VERSION_CODE` 才算有更新」；`code == VERSION_CODE` 时再比 `versionName` 字符串（忽略前缀 v）。
   `AppVersion.isCurrent(name)` 这个「资产名 vs 构建 tag」的错配直接去掉。
2. **加下载互斥**：`AtomicBoolean downloading`（照抄 `server/process/ApkUrlPush.java:57` 的写法）；
   下载中再点「检查更新」→ 直接提示「正在下载 x%」，不重新拉清单、不重下。
3. **持久化待安装**：prefs 记 `update_pending`（versionCode + 包路径 + sha256）。下载校验通过后写；安装器返回后仍留在；
   下次启动 `App.onCreate` 检查：包还在且校验通过 → 弹「可用的更新包，是否安装」；包丢了 → 清标记。
4. **启动自动检查（可选）**：`Setting.isUpdateAuto()` 已有开关（`update`，`Setting.java:801-807`），
   现在**没有任何地方用它做启动检查**。可以在第 1~3 条修好之后再挂上，否则会变成「每次启动都提示同版本」。
5. **安装权限预检**：清单已声明 `REQUEST_INSTALL_PACKAGES`，但代码没有 `canRequestPackageInstalls()` 预检。

**建议顺序**：先修 1（否则后面全是错的），再做 2/3，最后考虑 4。

## 6. 我的追更缺「已看第几集 / 更新至第几集」

### 现状：**布局和绑定代码都在**，是数据匹配没命中

- `adapter_vod.xml:52-86` 有 `historyProgress`（已看）与 `historyUpdate`（更新至）两个标签控件；
  `KeepAdapter.java:136-147` 也写了绑定逻辑。
- 「已看」拿不到的原因链（三道门槛，任一不满足就空）：
  1. `KeepAdapter.findHistory()` 用 **`cid + key` 精确匹配**（`:173-179`，SQL `WHERE cid=:cid AND key=:key`）——
     只要 Keep 里的 `cid` 和 History 行的 `cid` 不一致，就查不到 → **两个标签同时消失**。
     `cid` 是「配置 ID」（`VodConfig.getCid()`），**换配置/重新导入配置后会变**，这正是「又不见了」最可能的原因。
  2. 即使查到了 History，`position <= 0` 时 `HistoryProgressFormatter` 返回空串（`:143` 判空）。
  3. 「更新至」要 `count > 0`，来源是 `max(UpdateTrack.count, HistoryEpisodeCache, parseEpisode(vodRemarks))`，
     备注若是「HD」「国语」这类无数字文本，解析出 0。
- 另一个独立 bug：`KeepActivity.onCreate` 里 `UpdateTrack.markAllSeen()`（`:62-63`）在列表绑定**之前**执行，
  把 `seen` 拉到 `count` → 列表里的「有更新」红字（`count > seen`）**几乎永远不会显示**。

### 方案

1. `findHistory()` 改成「先 `cid+key`，未命中再退化到 `key`（跨 cid）」；必要时用 `vodName+siteKey` 兜底。
2. `markAllSeen()` 从 `onCreate` 移到「用户真正看到列表之后」（`onResume` 且列表已渲染），或改成只标记**当前可见项**。
3. 「更新至」的备注解析加一道：解析不到数字时，回退显示原始备注（如「更新至 HD」），而不是整条隐藏。

## 7. 历史合并（本地下载 / 站点注入 与 站点播放）

### 现状：**代码里明确禁止合并**

- `History.canMergeByName()` = `!isPushHistory()`，`isPushHistory()` 判 `key.startsWith("push_agent@@@")`
  （`History.java:338-344`）；`shouldMerge()` 第一句就把 push 记录排除（`:347`）。
- 本地下载的 key 形如 `push_agent@@@local:<siteKey>:<vodName>@@@cid`（`mobile/VideoActivity.java:512-514`），
  站点播放是 `<siteKey>@@@<vodId>@@@cid` → **id 段根本不同**，即使放开 push 判断也匹配不上。
- 站点注入的 key 是 `<siteKey>@@@<vodId>@@@<由configKey反查的cid>`（`PlaybackProgressInput.java:119-124`），
  与站点播放只差 `cid` 段 → 若 cid 一致本来就能合并，不一致就拆两条。

### 方案

1. **放开 push 合并**：`shouldMerge` 允许 push 记录参与，但用「`vodName` 完全相同 + 时长差 ≤10 分钟」这两个强条件兜住误合并
   （现有 `History.shouldMerge` 已经有同名 + 时长判据，放开 push 即可）。
2. **注入侧补「跨 cid 复用 key」**：`PlaybackProgressWriter` 已有「同 cid 内按前缀找本地 key」（`:249-277`），
   把查找范围放宽到跨 cid（按 `siteKey+vodId` 匹配），命中就复用同一 key。
3. 合并后保留哪条：优先保留「站点播放」那条（有集数/进度），把 push 记录的 `createTime` 与 `position` 合并过来。

**风险**：同名不同剧（如「第01集」命名的短剧）可能被误合并——建议只对「同名 + 同站点」生效，且保留原始记录 7 天再清（现在 `merge` 是立即 `delete`）。

## 9. 设置里增加首页推荐列表（豆瓣热播 / 站点推荐 / 最近观看）

### 现状

- 首页是「**一个 type 一个 tab，tab 内一个纵向列表**」（`TypeAdapter.java:36-51` + `TypeFragment.java:129-186`），
  **没有横向多行/分节的首页结构**。全工程唯一的横向 RecyclerView 是直播频道栏。
- **「站点推荐」其实已经有了**：spider 的 `homeVideoContent()` 结果被塞进伪 `home` tab（`SiteApi.java:63-69`、`TypeAdapter.java:47-51`）。
- **「豆瓣」全工程 0 处实现**（无 API 客户端、无缓存表、无 UI）。要接等于从零做第三方数据源。
- **「最近观看」**：`History.get()` 固定 `LIMIT 60`、**无 OFFSET**（`HistoryDao.java:19-20`），要当数据源得分页；
  且 `History` → `Vod` 需要一层映射（name/pic/remarks/siteKey/vodId）。

### 三条路线（按野心从小到大）

| 路线 | 内容 | 改动量 |
|---|---|---|
| **R1. 设置项 + 伪 tab（最省）** | 设置里加一个「首页推荐」多选（豆瓣热播/站点推荐/最近观看），选中的作为一个**额外 tab**（复用现有伪 `home` tab 机制） | 小～中 |
| **R2. TVBox 式分节首页** | 首页改成「多个横向行，每行一个数据源」，需要新增分节数据模型 + 行容器（Nested RecyclerView / ConcatAdapter）+ 行头「更多」 | 大 |
| **R3. R1 + 豆瓣数据源** | 在 R1 基础上接豆瓣（`movie.douban.com/j/search_subjects` 这类接口不稳定，需要自带兜底与缓存） | 中～大 |

**建议**：先做 R1 的「站点推荐 + 最近观看」（这两个数据都在本地，稳），豆瓣单独立项（依赖第三方接口可用性）。
