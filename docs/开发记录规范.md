# WebHomeTV 开发记录规范

> 最后更新：2026-10-31（第 16 轮）
> 适用范围：所有在本项目上工作的 agent 与人类开发者
> 目标：任何人（或任何 agent）接手后，能在 30 分钟内知道「现在是什么状态、为什么这样做、哪些坑不要再踩」

---

## 1. 总原则

1. **先记录，再动手**：每轮开始先确认轮次编号与当前 HEAD，开工后把过程写进当日 memory。
2. **结论必须落盘**：只写在对话里等于没写；对话会丢，磁盘不会。
3. **记录为交接服务**：记录的第一读者是「没参与过这轮工作的接手者」，而不是自己。
4. **记录可验证**：关键结论附文件路径、命令、提交号、SHA-256、设备与版本号。
5. **不重复堆砌**：同一信息只在一个文档写详细版，其它位置用链接，避免多份过期副本。
6. **脱敏**：口令、Token、密钥、账号一律不写进任何被提交的文档。

---

## 2. 记录层级与文件职责

| 层级 | 文件 | 写什么 | 不写什么 |
|---|---|---|---|
| 过程层 | `.workbuddy/memory/YYYY-MM-DD.md` | 当天做了什么、临时结论、失败尝试、命令 | 长期结论（会被汇总走） |
| 模块层 | `README.md` 对应章节 | 模块实现、代码位置、使用/验证方法、易踩坑 | 每轮流水账（只写与本模块相关的） |
| 汇总层 | `docs/开发记录总览.md` | 时间线、模块清单、坑的合辑、后续注意事项 | 命令的大段复制（链接到 README） |
| 入口层 | `docs/开发进度与交接.md` | 30 秒上手、当前状态、关键约定、链接 | 详细模块说明 |
| 规范层 | `docs/开发记录规范.md`（本文） | 流程、模板、提交/发布/交接规则 | 具体业务内容 |
| 专项层 | `docs/tangtv-*.md` | 方案、调研、评估、决策依据 | 与专项无关的进度 |

补充约定：

- **README 是模块手册**，新增功能必须在 README 有对应章节或小节，不能只存在于代码。
- **入口页永远保持短**（建议 ≤ 200 行），只放「现在」需要的信息；历史细节指向总览。
- **总览是唯一的时间线权威**，每轮结束追加一行，不删旧行（除非合并同类项并注明）。
- **不维护待办表**（用户 2026-10-31 明确要求）：任何文档都不列「下一步计划 / 待办清单 / 排期」。
  只记两类事实——**本轮做了什么**（入口页 §2.1、总览时间线）与**已知未解决的问题**（README 对应章节），
  需求由用户随时提出，不预先排期。

## 3. 何时必须记录

| 时机 | 必须做的事 |
|---|---|
| 每轮开始 | 建/续当日 memory；记录轮次编号、当前版本与 HEAD、本轮目标 |
| 方案定型前 | 把候选方案与取舍写进专项文档或 memory，避免只存在于对话 |
| 功能完成 | 更新 README 对应章节；补单测；在 memory 记录验证结果 |
| 修复 bug | 记录**根因**（不是「修好了」），写清触发条件与验证方法 |
| 构建/发布完成 | 登记变体、大小、SHA-256、签名、发布地址、清单 commit |
| 真机验证完成 | 登记设备型号/分辨率/系统版本、操作步骤、观察结果、包名与 SHA |
| 每轮结束 | 更新入口页「当前状态」；总览追加时间线；检查清单逐项打勾 |
| 交接前 | 按第 9 节交接流程自检，确保「有代码必有记录」 |
| 发现记录与代码不一致 | 当天修正记录，并在变更记录里注明「纠正」 |

**硬性要求**：一轮工作如果没有留下任何记录，视为未完成。

## 4. 轮次编号与命名

1. 轮次是**全局递增**的，不按天/按人重编号。当前最新为「第 16 轮」。
2. 每轮在入口页顶部写：`最后更新：YYYY-MM-DD（第 N 轮）`。
3. 一轮可包含多个提交，但只对应一个轮次编号。
4. 版本发布轮与功能轮可合并计数；纯文档轮也占一个编号。
5. 命名示例：
   - 提交：`feat(hls-adblock): 移植 HLS 结构化去广（三路径 + 32 个单测）`
   - 发布：`chore(release): 版本号 565 / 5.6.5`
   - 文档：`docs: 第 16 轮整合开发记录与规范`
6. 目录/文件命名：
   - 日常笔记：`.workbuddy/memory/YYYY-MM-DD.md`
   - 专项文档：`docs/<主题>-<类型>.md`（如 `tangtv-integration-plan.md`）
   - 不新建「开发记录2」「最终版」这类文件；更新原文件。

## 5. 每轮记录模板

复制以下模板到当日 memory 或入口页的「本轮变更」：

```markdown
## 第 N 轮｜YYYY-MM-DD｜<一句话标题>

### 需求与来源
- 用户原话/需求单：<摘录关键句>
- 验收标准：<可观察的结果 1~3 条>

### 方案与取舍
- 选定方案：<做什么>
- 否决方案：<不做什么，为什么>
- 影响范围：<模块 / 文件 / 是否影响 leanback>

### 改动
| 类型 | 文件 | 说明 |
|---|---|---|
| 新增 | `path/A.java` | ... |
| 修改 | `path/B.java` | ... |
| 删除 | `path/C.java` | ... |

### 验证
- 单测：<任务名 + 用例数/结果>
- 编译：<变体 + 成功/失败>
- 真机：<设备 + 分辨率 + 步骤 + 结果>
- 回归：<受影响功能的检查结果>

### 产物
| 项 | 值 |
|---|---|
| APK | <文件名 / 大小 / SHA-256 前 8 位> |
| 签名 | <debug / release CN=WebHTV> |
| 发布 | <GitHub Release / CNB 清单 commit> |

### 踩坑
1. <现象> → <根因> → <解决> → <以后怎么避免>

### 遗留（只记事实，不排期）
- <未解决的问题 / 未覆盖的场景：写清现状与线索，不写「下一步计划」>

### 提交
- `<hash>` <提交说明>
```

要求：

- 「踩坑」必须写根因，不能只写「已修复」。
- 「验证」必须能复现：命令、坐标、设备型号齐全。
- 「遗留」只记事实与线索（现象 + 已排查到哪一步），**不列待办、不排期、不进任何表**；
  已知问题统一落在 README 对应章节（如第六节「已知问题（留档）」）。

## 6. 提交规范

1. **一个可独立回滚的改动一个提交**；功能、修复、文档分离。
2. 提交信息格式：`<type>(<scope>): <中文说明>`，type 取 `feat` / `fix` / `docs` / `chore` / `refactor` / `test` / `ci`。
3. 说明写「为什么」，不写「改了哪些行」；细节放提交正文或文档。
4. 提交前必须：
   - `git status` 确认无意外文件（尤其 `local.properties`、`secrets/`、APK）；
   - 至少编译通过目标变体；
   - 涉及纯逻辑的补单测并跑通；
   - 文案三语、布局四套同步检查。
5. **禁止**：
   - `git push --force`（GitHub 分叉历史用重放脚本）；
   - 提交明文口令/Token/密钥；
   - 提交 `build/`、`.gradle/`、`.cxx/`、`*.apk`、`*.aab`。
6. 版本号规则：`versionCode = 5xx` 递增、`versionName` 同步；发布提交单独一条。

## 7. 构建与发布记录规范

### 7.1 构建记录必须包含

| 项 | 示例 |
|---|---|
| 变体 | `mobileArm64_v8a` |
| 构建方式 | `-PfastRelease=true`，容器 `hostroot:1` |
| 命令 | `/home/s/build/container-run.sh /home/s/build/build-mobile-arm64.sh release` |
| 签名 | release（`CN=WebHTV`，SHA-256 `5c3b6ccc…`） |
| 产物 | 大小、SHA-256 前 8 位、存放路径 |
| 校验 | `apksigner verify` 输出摘要 |

### 7.2 发布记录必须包含

1. 版本号与四变体产物表（即使本轮只打 mobile，也保留完整历史表并标注「未重新构建」）。
2. GitHub Release 地址、CNB 清单仓库与 commit。
3. 清单字段核对：`versionName` / `code` / `apk` / `size` / `sha256`。
4. 更新链路验证：直链 → 加速线路 → CNB 归档，至少验证一条实际可下载。

### 7.3 发布后检查

- [ ] 客户端「检查更新」能拿到新版本
- [ ] 清单 SHA-256 与 Release asset `digest` 一致
- [ ] 旧版本可覆盖安装（签名一致）
- [ ] 发布说明包含用户可感知的变更

## 8. 验证记录规范

### 8.1 单测

- 纯逻辑优先（URL 分类、m3u8 解析、规则匹配、弹幕解析、配置迁移）。
- 新增逻辑尽量配单测；修复 bug 优先补回归用例。
- 记录任务名、用例数、通过率；失败必须写根因与是否阻塞发布。

### 8.2 真机

每条验证记录至少包含：

```
设备：<型号 / 代号>，<分辨率>，Android <版本>
包：<包名>，<SHA-256 前 8 位>，<签名>
步骤：1) ... 2) ... 3) ...
结果：<通过/失败>；失败时附 logcat 关键行
```

要求：

- 每轮用户要求「直接 adb 操作验证」时，必须真机走查，不能只出包。
- 旋转、播放、下载、更新等关键路径必须双向/多路径验证。
- 保留可复现命令（`adb shell wm size`、`input tap` 坐标、`adb forward` 端口）。

### 8.3 验证门槛（最低集）

| 改动类型 | 最低验证 |
|---|---|
| 纯逻辑 | 对应单测 + 编译 |
| UI / 布局 | mobile 编译 + 真机小屏与横屏走查 |
| 播放 / 旋转 | 真机播放中横竖屏互切，画面/进度/选集连续 |
| 下载 | `M3u8Test` + leanback 编译 + 真机下载→暂停→续传→完成→本地播放→删除 |
| 弹幕 | 搜索 + 自动匹配 + 多源渐进式 + 关闭状态 |
| 更新/发布 | 直链 + 加速 + 归档三路径至少验一条，清单字段核对 |
| 云同步/公共配置 | 线上接口 curl + 真机登录/拉取/覆盖/恢复 |

## 9. 交接流程

### 9.1 交接前（交方）

1. 工作区干净：`git status` 无未提交改动（临时文件清理或明确说明）。
2. 更新入口页：当前版本、HEAD、风险、本轮结论。
3. 更新总览时间线：追加本轮一行。
4. 更新 README：新增/变更模块章节。
5. 确认「有代码必有记录」：入口页 2.2 的「过程缺失」清单如果存在，必须显式标注，不能假装有文档。
6. 产物与密钥：确认 APK/清单/签名文件位置；确认密钥未入库。
7. 写一条交接说明：本轮做了什么、没做什么、已知问题在哪（不写下一步计划）。

### 9.2 交接后（接方）

1. 按入口页「30 秒上手」跑一次构建或单测，确认环境可用。
2. 核对 `git log` 与入口页记录一致；不一致以代码为准并当天修正文档。
3. 阅读总览第 5 节「后续优化与注意事项」，不要重复已否决的方案。
4. 在当日 memory 写下接手确认与首个任务。

### 9.3 交接自检清单

- [ ] 入口页可在 5 分钟内读完并知道当前状态与关键约定
- [ ] 构建命令可复制即用（JDK/SDK/容器/挂载齐全）
- [ ] 签名与发布流程明确，密钥位置与安全边界清楚
- [ ] 「明确不做」项有理由（入口页 §2.3）
- [ ] 坑有根因与规避方法
- [ ] 记录中的文件路径/类名/命令真实存在
- [ ] 无明文口令、Token、密钥
- [ ] 版本号、HEAD、清单三方一致

## 10. 禁止事项

1. 禁止只在对话里给结论、不落盘。
2. 禁止把未验证的功能写成「已完成」。
3. 禁止删除或改写历史时间线来「美化」记录；纠正要标注「纠正」。
4. 禁止把过程性流水账塞进入口页（入口页只放当前状态）。
5. 禁止多份互相矛盾的「最终版」文档；同一主题只维护一份。
6. 禁止提交 `local.properties`、`secrets/`、APK/ABI 产物、构建缓存。
7. 禁止用 `git push --force` 覆盖远端历史。
8. 禁止整树 rsync 到构建副本（会覆盖调试签名配置）。
9. 禁止在未确认四套布局/三语文案同步的情况下提交 UI 改动。
10. 禁止把口令、Token、账号、证书密码写入任何会提交的文件。

## 11. 快速检查清单（每轮收工前）

- [ ] 轮次编号、日期、版本号、HEAD 已更新
- [ ] 改动文件清单完整（新增/修改/删除）
- [ ] 单测/编译/真机验证结果已记录
- [ ] 产物大小/SHA/签名/发布地址已登记
- [ ] 踩坑写了根因与规避
- [ ] 未解决问题以事实形式留在 README 对应章节
- [ ] README 对应章节已更新
- [ ] 总览时间线已追加
- [ ] 工作区干净，敏感信息未入库
- [ ] 下一位接手者读完入口页即可开工（不依赖任何待办表）
